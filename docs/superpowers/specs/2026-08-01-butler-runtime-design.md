# Study-Hub 管家运行时设计

日期：2026-08-01
状态：已实现并验证

## 定义

Study-Hub 管家运行时是一个项目内 MCP 能力层，不是新的聊天软件，也不是另一套提示词。用户继续在 Codex 里自然对话；Codex 负责理解、调查和修改，运行时负责保存任务事实、给出下一步、拦截越界操作并留下验证记录。

现有 Skill、内部角色、外部专家和 owner 文件继续是工作说明与领域知识来源。运行时不替代这些说明，也不让用户选择前端或后端。

## 组成与边界

| 部分 | 职责 |
|---|---|
| `backend/butler/` | 任务状态、SQLite 持久化、角色/专家目录、安全与完成闸门 |
| `backend/butler/mcp_tools.py` | 将运行时操作作为 MCP 工具暴露给 Codex |
| `backend/mcp_server.py` | 在不改变原有知识库工具的前提下注册 `butler_*` 工具 |
| `.claude/skills/butler/SKILL.md` | 唯一的管家入口规则：先建任务、每阶段读下一步、回写事实 |
| `project-memory/功能代号地图.md` | 来自真实前端路由的用户定位词典 |

## 流程约束

任务类型为 bug、功能改动、外部研究、项目体检、部署和记忆更新。它们都会保存原始描述、定位结果、角色交接、专家参与、尝试、确认、报告和验证。

- 高风险操作必须得到明确确认。
- 三次失败尝试自动停止，须由用户给出新方向恢复。
- 代码改动必须经过改动记录、六项审查和原始现象验证后才能完成。
- 研究、体检、部署和记忆更新必须有报告证据；部署额外需要核心流程验证。
- 记忆只形成草稿。用户确认草稿后，运行时仅记录待写入操作，永不自行写入项目记忆文件。

## 功能映射与验证证据

| 既有职责 | 运行时实现 | 验证 |
|---|---|---|
| 接收模糊问题与定位 | `butler_open_case`、`butler_record_context`、功能代号地图 | 运行时与 MCP 测试 |
| 内部角色和外部专家协作 | `butler_assign`、角色/专家目录与交接事件 | 普通 bug、跨前后端场景 |
| 高风险确认 | `butler_request_approval`、`butler_resolve_approval` | 高风险改动场景 |
| 受控循环 | `butler_record_attempt`、三次失败阻断、`butler_resume_case` | 运行时测试 |
| 改动审查与验收 | 改动、审查、验证、完成工具 | 普通 bug 场景与 MCP 全流程演练 |
| 研究和体检 | `butler_record_report` 与证据表 | 研究、健康检查场景 |
| 部署验证 | 部署报告后强制验证 | 部署场景 |
| 记忆退出协议 | 记忆草稿与确认记录 | 记忆更新场景 |

## 验收结果

自动化覆盖包含状态机、持久化、MCP 注册与响应、六类端到端场景。另完成了一次真实 stdio MCP 演练：创建 bug 任务、定位、分派、记录调查、实施、审查、验证并读取到 `completed` 状态。
