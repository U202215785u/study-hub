# AI 统一记忆层调研报告
版本：2026-05-29

## 背景

你的项目（study-hub）目前使用 Markdown 文件作为 AI 的"记忆"——功能角色定义、领域专家知识、问题追踪、状态记录都写在 `.md` 文件里，由 AI 每次对话时加载。这种模式简单有效，但有一个根本限制：**不同 AI 工具之间无法共享记忆**。

你在 Kimi 里和 AI 讨论的设计决策，切换到 Claude 或 GPT 时就全部丢失。每个 AI 都是"失忆"的，需要重新加载文件。你问的是：有没有让不同 AI 共享记忆的方案？

答案是：**有，而且已经有不少成熟项目和开源方案。**

---

## 核心问题定义

> 如何让多个 AI 工具（Kimi、Claude、GPT、Cursor 等）访问同一个记忆层，使得在一个工具里积累的知识，在另一个工具里也能被召回？

这和你的 `project-memory/` 系统的本质一样——只是从"文件系统"升级到"结构化记忆服务"。

---

## 方案分类

### 方案一：Hooks 被动日志 + 离线蒸馏（TowardsDataScience 方案）

**核心思路**：在 AI 工具外部挂接 Hooks，被动捕获所有会话事件，存入 Neo4j，再离线蒸馏成 Markdown 记忆。

**三层架构**：
1. **Hooks（在线）**：Claude Code / Codex / Cursor 的生命周期事件（session start、prompt、tool use、session end）→ 被动写入 Neo4j
2. **Dream phase（离线）**：批处理读取事件，让 Claude 蒸馏成 durable markdown memories，按主题合并而非追加
3. **Injection（在线）**：下次任意工具启动时，自动加载 profile memories；每次 prompt 时搜索相关记忆注入上下文

**优点**：
- 不依赖 AI 主动"记住"——确定性捕获
- 跨工具共享：Cursor 的会话，Claude Code 也能看到
- 记忆会合并更新，不会无限增长

**缺点**：
- 需要为每个工具写 Hook 适配器
- 离线蒸馏有延迟，不是实时
- 需要 Neo4j + 批处理任务

**参考**：https://towardsdatascience.com/unified-agentic-memory-across-harnesses-using-hooks/

---

### 方案二：MCP Memory Service（mcp-memory-service）

**核心思路**：一个自托管的 REST API + MCP 服务，所有 AI 工具通过 MCP 协议读写同一个记忆后端。

**架构**：
- 后端：知识图谱 + 向量检索 + SQLite
- 接口：REST API + MCP Server
- 客户端：Claude Code、Cursor、VS Code、ChatGPT（Developer Mode）等任何 MCP 兼容工具

**记忆类型**：
- 决策记忆（decisions）
- 因果知识图谱（causal knowledge graphs）
- 实体关系（entities & relationships）

**优点**：
- 一行命令启动，零配置
- 5ms 检索延迟
- 支持 OAuth、团队协作
- 有可视化 Dashboard

**缺点**：
- 需要额外维护一个服务
- 记忆格式受限于服务定义

**参考**：https://github.com/doobidoo/mcp-memory-service

---

### 方案三：Mem0（最成熟的商业/开源方案）

**核心思路**：为 AI Agent 提供通用记忆层，支持向量+图谱+KV 混合存储，自适应更新。

**架构**：
- 存储：Vector DB（Qdrant/Chroma/Milvus）+ Graph + KV Store
- 检索：语义相似度 + 结构化过滤（user_id + agent_id + run_id + app_id）
- 更新：自动提取事实、合并更新、自适应遗忘

**多 Agent 隔离**：
```python
# Billing agent 存记忆
client.add("Customer upgraded to Pro", user_id="cust_123", agent_id="billing")

# Support agent 存记忆
client.add("Customer reported latency", user_id="cust_123", agent_id="support")

# 各自只能看到各自的记忆
billing_results = client.search("What plan?", filters={"agent_id": "billing"})
```

**优点**：
- 50,000+ 开发者使用，最成熟
- 支持 LangGraph、CrewAI、AutoGen
- 记忆压缩引擎减少 80% token
- 开源 + 托管云两种选择

**缺点**：
- 云版有费用
- 自托管需要维护向量数据库

**参考**：https://mem0.ai

---

### 方案四：Letta（原 MemGPT）—— 三级内存管理

**核心思路**：把 LLM 上下文当作虚拟内存来管理——Core（RAM）+ Recall（磁盘缓存）+ Archival（冷存储）。

**三层内存**：
- **Core Memory**：始终在上下文里（用户画像、当前任务）
- **Recall Memory**：可搜索的近期历史（过去 N 条消息）
- **Archival Memory**：长期存储，按需检索

**特点**：
- 不是简单的 RAG，而是运行时主动管理记忆升降级
- Agent 自己决定什么时候把记忆从 Archival 提升到 Recall
- 支持 Memory Blocks（结构化数据容器）

**优点**：
- 长运行 Agent（数周）保持连贯性
- 有"时间感"的 episodic memory
- 开源 + 商业云

**缺点**：
- 必须采用 Letta 的运行时，不好剥离
- 运维复杂度高

**参考**：https://letta.com

---

### 方案五：Zep（时序知识图谱）

**核心思路**：基于时序的知识图谱，存储对话历史、提取实体和关系、支持时间感知的语义搜索。

**特点**：
- 自动从对话中提取事实和实体
- 构建 temporal knowledge graph
- 支持 LangChain、LangGraph、Flowise

**参考**：https://getzep.com

---

### 方案六：Agent Memory（SQLite 本地记忆）

**核心思路**：极简的 SQLite 本地服务器，为 AI Agent 提供共享持久记忆。

**特点**：
- SQLite 后端，零依赖
- 支持语义嵌入提升检索质量
- 适配 Codex、Claude Code

**参考**：https://mcpmarket.com/zh/server/agent-memory-2

## 对比总结

| 方案 | 复杂度 | 跨工具 | 自托管 | 知识图谱 | 适合场景 |
|------|--------|--------|--------|----------|----------|
| Hooks + Neo4j | 高 | ✅ | ✅ | ✅ | 深度定制、已有 Neo4j |
| MCP Memory Service | 中 | ✅ | ✅ | ✅ | 快速启动、团队协作 |
| Mem0 | 中 | ✅ | ✅/☁️ | ✅ | 生产环境、多框架 |
| Letta | 高 | ❌（绑定运行时） | ✅/☁️ | ❌ | 长运行自主 Agent |
| Zep | 中 | ✅ | ✅/☁️ | ✅ | 对话型 AI、客服 |
| Agent Memory | 低 | ✅ | ✅ | ❌ | 极简本地部署 |

## 对你项目的启示

你的 `study-hub/project-memory/` 系统其实已经是一个**简化版的统一记忆层**：

| 你的系统 | 对应成熟方案 |
|---------|------------|
| `状态.md` / `决策.md` / `问题.md` | Mem0 的 Profile Memory / Archival Memory |
| 领域专家的"活跃记忆"（陷阱、实验记录） | Mem0 的 fact extraction |
| 层级记忆（全局→模块→子模块） | Mem0 的 namespace scoping |
| Markdown 文件格式 | Hooks 方案的 distilled markdown memories |

**你可以考虑的演进方向**：

### 方向 A：保持文件系统，增加结构化索引
- 继续用 Markdown 文件
- 增加一个 SQLite/ChromaDB 索引层，自动提取文件中的关键信息
- AI 对话时先查索引，再按需加载文件
- **优点**：改动最小，保留完全控制权
- **缺点**：跨工具共享仍需手动加载文件

### 方向 B：接入 MCP Memory Service
- 部署 `mcp-memory-service`
- 把项目决策、陷阱、实验记录写入 MCP 服务
- Kimi / Claude / Cursor 都通过 MCP 读取
- **优点**：真正的跨工具共享
- **缺点**：需要维护一个服务

### 方向 C：自建轻量级记忆服务
- 基于 SQLite + FastAPI 自建
- 定义记忆类型：决策、陷阱、实验、问题
- 提供 REST API，各 AI 工具通过 API 读写
- **优点**：完全自定义格式，和你的项目深度绑定
- **缺点**：开发成本高

## 推荐下一步

如果你想**最小成本验证**跨 AI 记忆共享的价值：

1. **先试用 Mem0 开源版**（pip install mem0ai）
2. 把你的 `project-memory` 内容导入 Mem0
3. 在 Kimi 和 Claude 中分别测试记忆召回
4. 评估是否值得投入自建

如果你想**保持现有文件系统但增强检索**：

1. 用 ChromaDB 或 SQLite 建立一个索引层
2. 自动解析 Markdown 文件，提取关键段落
3. AI 对话时先语义搜索索引，再加载对应文件
