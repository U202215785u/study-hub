# Study Hub 体验稳定化与产品化全量执行方案

最后更新：2026-06-06  
关联总方案：`study-hub/project-memory/ux/体验稳定化与产品化总方案.md`  
定位：把总方案拆成可执行的全阶段流程、迭代机制、产物清单和每一步操作说明

---

## 1. 方案用途

本文件是“总指挥执行手册”。

总方案回答：

- 为什么进入体验稳定化与产品化阶段。
- 该阶段有哪些原则。
- 模块如何分层。
- 问题如何分级。
- 小方案应该长什么样。

本执行方案回答：

- 先做哪一步，后做哪一步。
- 每一步输入什么，输出什么。
- 每轮迭代怎么开始、怎么结束。
- 每个模块的小方案如何从总方案派生。
- 问题如何进入队列、如何修复、如何回归。
- 哪些文档必须更新。
- 哪些情况允许插队。
- 什么时候进入下一轮。

本文件不直接规定具体代码实现。具体代码实现由每个模块的小方案和实施计划决定。

---

## 2. 总体执行结构

整个阶段拆成 5 个层级。

```text
L0 阶段治理
  -> 定义节奏、分级、文档、验收口径

L1 全量盘点
  -> 梳理所有模块、路径、问题、风险

L2 模块小方案
  -> 每次只制定一个模块或一条路径的方案

L3 实施迭代
  -> 按小方案修复、验证、回归

L4 沉淀复用
  -> 把通用组件、规范、测试脚本沉淀下来
```

所有执行都遵循同一个闭环：

```text
发现
  -> 记录
  -> 分级
  -> 进入小方案
  -> 实施
  -> 验证
  -> 归档
  -> 复盘
```

## 3. 阶段角色与职责

这里的“角色”可以由人承担，也可以由 Agent 按任务扮演。关键是职责要清楚。

| 角色 | 职责 | 主要产物 |
|---|---|---|
| 总指挥 | 控制阶段节奏、优先级、范围、验收口径 | 本执行方案、阶段看板、迭代复盘 |
| UX Owner | 设计走查脚本、执行体验评估、维护 UX 问题追踪 | 测试脚本、体验报告、问题追踪 |
| 模块 Owner | 解释模块现状、定义核心路径、制定小方案 | 模块小方案、模块状态更新 |
| Frontend Owner | 实现前端交互、视觉、组件、响应式修复 | 前端改动、组件规范、构建验证 |
| Backend Owner | 修复 API、启动、数据、错误处理、配置问题 | 后端改动、测试结果、问题记录 |
| QA/验证角色 | 执行回归、边界测试、截图验证 | 验证记录、回归报告 |
| UI 系统 Owner | 抽象通用组件和设计变量 | 设计规范、组件规范、复用清单 |

一个人可以同时承担多个角色，但每个任务开始时必须明确当前视角。

## 5. 全阶段路线图

### 5.1 Phase 0：启动与基线建立

目标：建立全项目体验基线，不急于修复。

输入：

- 总方案
- 项目状态文档
- 各模块状态和问题文档
- 已有 UX 报告
- 当前代码结构

步骤：

1. 确认当前阶段入口。
2. 建立模块清单。
3. 为高频模块定义核心路径。
4. 整理现有 P0/P1/P2/P3 问题。
5. 为每个高频模块补齐或创建体验测试脚本。
6. 执行第一批体验走查。
7. 形成基线评分。
8. 生成第一版优先级队列。

输出：

- 高频模块核心路径表
- UX 问题总表
- 第一版优先级队列
- 基线体验报告
- 第一批模块小方案候选列表

完成标准：

- Wiki、Home、Automation、Journal、Search Assistant 至少有核心路径定义。
- Wiki 已有报告被纳入基线。
- P0/P1 问题有明确列表。
- 下一轮优先处理模块已经确定。

### 5.2 Phase 1：核心路径稳定化

目标：清理 P0/P1，让高频路径稳定可用。

输入：

- Phase 0 的优先级队列
- 模块小方案
- 复现步骤
- 验收标准

步骤：

1. 选择一个模块或一条路径。
2. 制定小方案。
3. 根据小方案拆实施任务。
4. 先补验证用例或测试脚本。
5. 修复 P0/P1。
6. 执行构建、接口测试或浏览器走查。
7. 回归原问题。
8. 更新问题追踪和模块状态。
9. 记录可复用经验。

输出：

- 已实施的小方案
- 修复记录
- 验证记录
- 回归报告
- 更新后的问题追踪

完成标准：

- 高频模块没有长期积压的 P0。
- 当前小方案覆盖的 P1 已验证修复或明确阻塞。
- 回归后没有新增同级别阻断问题。

### 5.3 Phase 2：体验一致性

目标：解决关键 P2，并开始形成统一体验组件。

输入：

- 已稳定的核心路径
- 高频出现的 P2 问题
- 重复实现的组件或样式

步骤：

1. 从问题追踪中找出跨模块重复问题。
2. 判断是否需要通用组件或规范。
3. 选择一个真实模块作为落地点。
4. 制定组件/规范小方案。
5. 在一个模块中实现并验证。
6. 推广到第二个模块。
7. 更新 UI 规范。
8. 更新问题追踪中对应 P2 状态。

输出：

- 初版 Toast/Loading/Error/Empty 等组件规范
- 组件使用示例
- 至少两个模块的复用落地
- UI 规范更新

完成标准：

- 反馈类体验不再每个页面各写一套。
- 用户能在不同模块看到一致的成功、失败、加载、空状态表达。
- 至少有一批硬编码色值或重复样式被收敛。

### 5.4 Phase 3：边界强化与产品美化

目标：让产品能承受真实使用中的复杂数据和异常情况，并提升整体质感。

输入：

- 核心路径稳定结果
- 边界测试矩阵
- 视觉问题 backlog
- 用户真实反馈

步骤：

1. 为每个高频模块选择适用边界场景。
2. 构造测试数据或模拟失败场景。
3. 执行边界测试。
4. 将失败项分级。
5. 修复高优先级边界问题。
6. 做移动端和窄屏验证。
7. 做视觉层级、间距、色彩、动效精修。
8. 更新设计规范。
9. 生成阶段体验对比报告。

输出：

- 边界测试报告
- 移动端验证记录
- 视觉精修记录
- 设计规范初版
- 阶段体验对比报告

完成标准：

- 高频模块在空数据、长内容、网络错误、重复点击场景下不崩。
- 主要页面视觉风格统一。
- 高频模块综合评分接近或达到 4.0/5。

### 5.5 Phase 4：制度化与持续运行

目标：让体验稳定化成为后续开发默认流程。

输入：

- 前三阶段沉淀的模板、规范、报告
- 新功能需求
- 用户反馈

步骤：

1. 把“核心路径 + 边界测试 + 验收标准”加入新功能小方案模板。
2. 每个新功能默认写体验检查点。
3. 每周或每批任务更新问题追踪。
4. 每月做一次体验评分回顾。
5. 对长期未处理 P2/P3 做裁剪或排期。
6. 对已废弃问题归档。

输出：

- 常态化体验治理规则
- 新功能体验验收模板
- 月度体验回顾
- 精简后的 backlog

完成标准：

- 新功能不会绕过体验验收。
- 问题追踪表不是摆设，而是持续维护。
- 体验规范能指导实际实现。

## 6. 单轮迭代标准流程

每一轮迭代建议命名为：

```text
UX-R[轮次]-[模块]-[主题]
```

示例：

```text
UX-R1-Wiki-CorePath
UX-R2-Home-Feedback
UX-R3-Automation-ErrorRecovery
```

### 6.1 迭代入口

开始一轮前，必须明确：

- 模块：
- 主题：
- 本轮目标：
- 本轮不做：
- 关联问题：
- 验收方式：

输出文件：

```text
study-hub/project-memory/ux/plans/YYYY-MM-DD-[module]-[topic].md
```

### 6.2 迭代计划

每轮小方案至少拆成 6 个任务包。

| 任务包 | 内容 | 输出 |
|---|---|---|
| T1 现状确认 | 读文档、读代码、复现问题 | 现状摘要 |
| T2 路径定义 | 写清用户路径和成功标准 | 核心路径表 |
| T3 问题分级 | P0/P1/P2/P3 分类 | 问题表 |
| T4 方案设计 | 交互、状态、错误、视觉、边界 | 小方案 |
| T5 实施修复 | 按任务改代码或配置 | 代码改动 |
| T6 验证沉淀 | 测试、截图、报告、规范更新 | 回归记录 |

### 6.3 迭代执行

每轮按以下顺序执行。

#### Step 1：读取上下文

做什么：

- 读总方案。
- 读全量执行方案。
- 读模块状态。
- 读模块问题。
- 读相关 UX 报告。
- 读相关代码入口。

输出：

```md
## 当前状态摘要

- 模块：
- 已完成能力：
- 已知问题：
- 核心路径：
- 技术风险：
- 本轮建议范围：
```

#### Step 2：确认范围

做什么：

- 从问题表中选出本轮处理项。
- 明确不处理项。
- 如果 P0 出现，先切换到 P0 修复。

输出：

```md
## 本轮范围

处理：
- UX-xxx

不处理：
- UX-yyy，原因：
```

#### Step 3：写小方案

做什么：

- 使用总方案里的小方案模板。
- 写明交互、状态、错误、视觉、边界测试。

输出：

```text
ux/plans/YYYY-MM-DD-[module]-[topic].md
```

#### Step 4：写验证清单

做什么：

- 把小方案验收标准拆成可执行 checklist。
- 明确要跑哪些命令。
- 明确要用浏览器看哪些页面。

输出：

```md
## 验证清单

- [ ] 命令验证：
- [ ] 浏览器验证：
- [ ] 边界验证：
- [ ] 文档更新：
```

#### Step 5：实施

做什么：

- 先修 P0/P1。
- 再修本轮选定 P2。
- 只在必要时处理 P3。
- 如果发现范围外严重问题，记录并评估是否插队。

输出：

- 代码改动
- 配置改动
- 测试改动
- 文档改动

#### Step 6：验证

做什么：

- 跑对应测试。
- 跑构建或启动检查。
- 用浏览器回归核心路径。
- 验证边界场景。

输出：

```md
## 验证记录

- 命令：
- 结果：
- 浏览器路径：
- 发现问题：
- 是否通过：
```

#### Step 7：问题追踪更新

做什么：

- 已修复问题移动到已修复区。
- 未修复问题保留活跃状态。
- 新发现问题新增编号。
- 废弃问题写明原因。

输出：

- `ux/问题追踪.md` 更新
- 模块 `问题.md` 更新

#### Step 8：沉淀规范

做什么：

- 如果出现可复用组件，写入 UI 规范。
- 如果出现新陷阱，写入对应模块问题或记忆。
- 如果脚本需要调整，更新测试脚本。

输出：

- `ui/设计规范.md`
- `ui/组件规范.md`
- `ux/脚本模板.md`
- 对应模块 `状态.md`

#### Step 9：迭代复盘

做什么：

- 写本轮完成了什么。
- 写还剩什么。
- 写下一轮建议。

输出：

```md
## 迭代复盘

- 本轮完成：
- 未完成：
- 新增问题：
- 复用沉淀：
- 下一轮建议：
```

## 7. 每日/每次工作节奏

如果一天内只做一小段，也按这个节奏。

### 7.1 开始前 10 分钟

做什么：

1. 看 `ux/状态.md`。
2. 看当前模块小方案。
3. 看相关问题编号。
4. 确认今天只做哪几个检查项。

输出：

- 今日目标一句话。
- 今日不做事项。

### 7.2 工作中

做什么：

1. 每完成一个小步骤就更新 checklist。
2. 遇到范围外问题先记录，不立刻扩散。
3. 如果发现 P0，暂停当前任务，切换 P0。
4. 如果发现设计系统重复问题，标记为“可沉淀”。

输出：

- 小方案 checklist 更新。
- 问题追踪临时条目。

### 7.3 结束前 15 分钟

做什么：

1. 跑能跑的验证。
2. 更新文档状态。
3. 标记问题状态。
4. 写下一步建议。

输出：

- 验证记录。
- 更新后的状态文档。
- 下一步任务。

## 8. 问题流转机制

### 8.1 问题状态

所有体验问题使用以下状态。

| 状态 | 含义 |
|---|---|
| 待确认 | 已观察到，但缺少复现或影响判断 |
| 待修复 | 已确认，需要进入小方案或修复队列 |
| 修复中 | 当前迭代正在处理 |
| 待验证 | 代码已改，等待回归 |
| 已修复 | 回归通过 |
| 已废弃 | 功能变化或判断变化，不再处理 |
| 阻塞 | 需要外部条件或上游问题解决 |

### 8.2 问题编号

推荐编号：

```text
UX-[模块]-[三位数字]
```

示例：

```text
UX-Wiki-001
UX-Home-001
UX-Automation-001
UX-Journal-001
UX-SearchAssistant-001
```

跨模块问题：

```text
UX-UI-001
UX-System-001
```

### 8.3 问题进入规则

问题进入追踪表必须满足至少 3 项：

- 有明确页面或模块。
- 有实际行为描述。
- 有期望行为。
- 有复现步骤。
- 有截图或文字证据。
- 能判断用户影响。

### 8.4 问题插队规则

允许插队的情况：

- P0。
- 新增 P1 且阻断当前迭代核心路径。
- 数据丢失风险。
- 安全风险。
- 构建或服务启动失败。

不允许插队的情况：

- 只是视觉上想顺手改。
- P3 美化。
- 与当前路径无关的重构。
- 没有复现的问题。

## 9. 小方案制定流程

每个小方案必须经过 7 步。

### 9.1 Step 1：确定对象

做什么：

- 选择一个模块、路径或通用组件。

输出：

```text
对象：[模块/路径/组件]
```

示例：

```text
对象：Wiki 编辑与搜索核心路径
```

### 9.2 Step 2：收集上下文

做什么：

- 读取模块状态。
- 读取模块问题。
- 读取相关 UX 报告。
- 读取相关代码文件列表。

输出：

```md
## 上下文摘要

- 相关文档：
- 相关文件：
- 已知问题：
- 最近变更：
```

### 9.3 Step 3：定义核心路径

做什么：

- 写 1-3 条路径。
- 每条路径都写成功标准。

输出：

```md
## 核心路径

### 路径 1：xxx

1. 用户从 xxx 进入
2. 用户执行 xxx
3. 系统反馈 xxx
4. 用户得到 xxx

成功标准：
- 
```

### 9.4 Step 4：选择本轮问题

做什么：

- 按 P0/P1/P2/P3 选择本轮处理项。
- 明确不处理项。

输出：

```md
## 本轮问题选择

处理：
- UX-xxx

不处理：
```

## 11. 验证体系

### 11.1 命令验证

前端常用：

```text
cd study-hub/frontend
npm run build
```

后端常用：

```text
cd study-hub/backend
python -m pytest
```

如果当前 Windows Python 环境存在已知问题，按项目已有启动脚本和问题文档选择可用命令，不强行使用失效 venv。

### 11.2 浏览器验证

适用场景：

- 页面布局。
- 弹窗。
- 搜索。
- 表单。
- 长任务状态。
- 移动端。
- 视觉细节。

每次浏览器验证要记录：

- URL。
- 视口尺寸。
- 操作路径。
- 实际结果。
- 截图路径，如有。

### 11.3 数据验证

适用场景：

- 新建、编辑、删除。
- 解析入库。
- 排序筛选。
- 数据迁移。

记录：

- 操作前数据。
- 操作后数据。
- API 返回。
- 数据库或页面显示是否一致。

### 11.4 边界验证

每个高频模块至少覆盖：

- 空数据。
- 长内容。
- 网络/API 错误。
- 重复点击。
- 移动端或窄屏。

如果某项暂时无法模拟，必须写明原因。

## 12. 设计系统落地机制

### 12.1 何时抽组件

满足任一条件即可考虑抽组件：

- 同一 UI 模式出现 3 次以上。
- 两个高频模块都需要同一种反馈。
- 当前重复实现已经导致样式或行为不一致。
- 未来小方案明确会继续使用。

不抽组件的情况：

- 只出现一次。
- 需求还不稳定。
- 抽象会显著增加实现复杂度。

### 12.2 组件沉淀顺序

第一批：

1. Toast
2. Loading
3. Error State
4. Empty State

第二批：

1. Modal
2. Drawer
3. Toolbar
4. Confirm Dialog

第三批：

1. Button
2. Tag/Badge
3. Form Field
4. Status Badge

第四批：

1. 页面布局规则
2. 色彩变量
3. 间距变量
4. 字体层级

### 12.3 每次沉淀必须输出

```md
## 组件/规范记录

- 名称：
- 解决的问题：
- 使用场景：
- 不适用场景：
- 交互规则：
- 视觉规则：
- 已落地模块：
- 后续迁移模块：
```

## 13. 模块执行顺序与详细产物

### 13.1 Wiki

阶段目标：

- 把 Wiki 作为样板模块，跑通完整闭环。

核心路径：

1. 进入 Wiki -> 查找文章 -> 阅读文章。
2. 进入 Wiki -> 新建文章 -> 保存 -> 再次查看。
3. 进入 Wiki -> 编辑文章 -> 保存 -> 回到阅读态。

第一批产物：

- `ux/plans/YYYY-MM-DD-wiki-core-path.md`
- `ux/scripts/wiki-体验测试.md` 更新
- `ux/reports/wiki-体验报告-YYYYMMDD.md`
- `ux/问题追踪.md` Wiki 区更新

重点问题：

- 编辑路径。
- 新建入口。
- 搜索入口。
- 元信息拥挤。
- 主题切换可发现性。

### 13.2 Home

阶段目标：

- 让首页成为清晰稳定的操作入口。

核心路径：

1. 打开 Home -> 使用搜索/启动器 -> 进入外部或内部目标。
2. 打开 Home -> 查看最近文档 -> 预览/复制/删除。
3. 打开 Home -> 查看队列状态 -> 进入结果。

第一批产物：

- `ux/plans/YYYY-MM-DD-home-entry-feedback.md`
- `ux/scripts/home-体验测试.md`
- `ux/reports/home-体验报告-YYYYMMDD.md`
- `frontend/问题.md` 更新

重点问题：

- 启动器反馈。
- 最近文档操作一致性。
- 搜索和排序入口。
- 全局 Toast 统一。

### 13.3 Automation

阶段目标：

- 让长任务解析过程可理解、可等待、可恢复。

核心路径：

1. 提交链接 -> 看到任务创建成功。
2. 查看解析进度 -> 等待完成。
3. 打开结果 -> 文档入库并可再次查看。
4. 解析失败 -> 看到原因 -> 重试或复制诊断信息。

第一批产物：

- `ux/plans/YYYY-MM-DD-automation-progress-error.md`
- `ux/scripts/automation-体验测试.md`
- `ux/reports/automation-体验报告-YYYYMMDD.md`

重点问题：

- 队列状态。
- 长任务反馈。
- 失败原因。
- 重试机制。
- 结果刷新。

### 13.4 Journal

阶段目标：

- 保持手账的情绪化体验，同时保证记录和回顾路径顺。

核心路径：

1. 进入 Journal -> 记录今日内容 -> 保存。
2. 选择日期 -> 查看历史记录。
3. 查看统计/随机回顾 -> 回到某篇记录。

第一批产物：

- 移动端记录体验。
- 视觉温度。

### 13.5 Search Assistant

阶段目标：

核心路径：

## 16. 决策规则

### 16.1 是否进入小方案

满足以下条件即可进入小方案：

- 属于高频模块。
- 有明确核心路径。
- 至少有一个 P1 或两个以上 P2。
- 或者该模块是当前样板模块。

### 16.2 是否进入实施

小方案进入实施前必须具备：

- 本轮目标。
- 不做事项。
- 问题清单。
- 交互设计。
- 边界测试。
- 验收标准。

缺少任意一项，不进入实施。

### 16.3 是否结束一轮

一轮结束必须满足：

- 本轮处理项有明确状态。
- 关键验证已执行。
- 问题追踪已更新。
- 模块状态已更新。
- 下一步建议已写。

如果修复失败，也可以结束，但必须标为阻塞或遗留，并写清原因。

### 16.4 是否抽象通用组件

满足以下条件时抽象：

- 重复出现。
- 行为规则稳定。
- 至少两个模块会使用。
- 抽象后不会显著拖慢当前 P1 修复。

否则先局部修。

## 17. 风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 范围膨胀 | 一轮想修多个模块 | 每轮只允许一个主对象 |
| 美化先行 | 主路径未通就改视觉 | P0/P1 优先级强制高于 P2/P3 |
| 文档不更新 | 修了但追踪表过期 | 每轮结束前文档更新是验收项 |
| 验证不足 | 只跑构建，不走页面 | 命令验证 + 浏览器验证分开记录 |
| 抽象过早 | 为一次性 UI 抽组件 | 至少两模块或三次重复再抽 |
| 技术债扩散 | 顺手重构无关文件 | 小方案限定相关文件 |
| 多 Agent 冲突 | 同时改同一模块 | 任务开始前看 git status 和状态文档 |
| Windows 环境坑 | Python、路径、360、端口问题 | 使用项目已有启动/构建脚本，记录验证命令 |
