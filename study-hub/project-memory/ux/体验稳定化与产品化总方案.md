# Study Hub 体验稳定化与产品化总方案

最后更新：2026-06-06  
阶段定位：基础功能完成后的交互优化、Bug 修复、边界测试、体验优化、设计美化总方案

---

## 1. 阶段判断

Study Hub 当前已经跨过“把功能做出来”的阶段，进入“把功能变成可靠产品”的阶段。

这个阶段不以新增功能数量作为主要成果，而以以下结果作为判断标准：

- 核心路径稳定：用户能完整完成高频任务，不被中断、不迷路。
- 状态反馈清晰：加载中、成功、失败、空数据、异常状态都有明确表达。
- 边界情况可控：空数据、长内容、网络错误、重复点击、接口超时等不会让体验崩掉。
- 视觉语言统一：不同模块像一个产品，而不是多个页面拼接。
- 问题闭环可追踪：发现问题、制定小方案、修复、验证、沉淀规范形成循环。

本阶段的关键词是：稳定、清晰、一致、可验证、可持续。

---

## 2. 总目标

### 2.1 产品目标

把 Study Hub 从“功能集合”打磨为“学习与创作操作系统”。

用户在使用时应感到：

- 入口明确：知道从哪里开始。
- 操作顺手：主要动作不需要猜。
- 反馈及时：每一步系统都告诉用户发生了什么。
- 错误可恢复：失败后知道原因，也知道下一步怎么办。
- 信息有秩序：页面密度高但不乱。
- 风格可信：视觉不追求炫技，而是稳定、温暖、耐用。

### 2.2 工程目标

建立一套可复用的质量推进机制，让后续每个模块都能按相同流程被打磨：

```text
模块盘点
  -> 核心路径定义
  -> 体验走查
  -> 问题分级
  -> 小方案制定
  -> 实现修复
  -> 回归验证
  -> 规范沉淀
```

每个模块的小方案都必须能回答：

- 本模块用户最重要的任务是什么？
- 当前最影响任务完成的问题是什么？
- 本轮只解决哪些问题？
- 不解决哪些问题？
- 怎么验证体验确实变好了？
- 哪些东西应该沉淀为通用规范？

## 3. 工作原则

### 3.1 先稳定，再美化

如果核心路径不稳定，视觉美化只能制造更漂亮的不确定性。

优先级应始终是：

```text
P0 系统不可用
  > P1 核心路径阻断
  > P2 明显体验问题
  > P3 美化与增强
```

### 3.2 按路径优化，不按页面感觉优化

不要因为“这个页面看起来不够好”就开始改。

每次优化都要绑定一条用户路径，例如：

- 进入 Wiki -> 搜索文章 -> 阅读 -> 编辑 -> 保存 -> 再次查看
- 提交视频链接 -> 查看解析进度 -> 生成摘要 -> 进入知识库
- 打开首页 -> 搜索/启动常用工具 -> 查看最近文档 -> 继续学习

页面只是路径的一部分，真正要优化的是任务完成过程。

### 3.3 小批量闭环

每轮小方案必须控制范围。

推荐一轮只处理：

- 1 个模块，或
- 1 条跨模块路径，或
- 1 组通用组件问题

避免同时做“Wiki + Home + Automation + 视觉重构 + 后端稳定性”。这种范围会让验证变得模糊。

### 3.4 体验问题必须可复现

每个问题至少包含：

- 问题描述
- 级别
- 复现步骤
- 期望行为
- 实际行为
- 影响范围
- 验证方式

没有复现步骤的问题可以先进入观察区，但不直接进入修复队列。

### 3.5 设计系统从真实修复中长出来

不建议先闭门设计一整套 UI 系统。

更合适的方式是：

- 修 Wiki 弹窗时沉淀 Modal 规则。
- 修 Home 操作反馈时沉淀 Toast 规则。
- 修 Automation 队列时沉淀 Loading/Progress 规则。
- 修空数据页面时沉淀 Empty State 规则。

这样设计系统不会脱离实际使用场景。

## 4. 模块分层

### 4.1 第一层：高频主路径模块

这些模块优先打磨，因为它们决定用户对产品的主要印象。

| 模块 | 当前定位 | 打磨重点 |
|---|---|---|
| Home | 学习操作系统入口 | 启动效率、最近文档、搜索、任务状态、入口可发现性 |
| Wiki | 知识沉淀与阅读 | 搜索、阅读、编辑、新建、元信息、主题切换 |
| Automation | 内容解析与入库 | 进度反馈、错误恢复、队列状态、结果刷新 |
| Journal | 手账与回顾 | 情绪化表达、记录效率、回顾体验、视觉温度 |
| Search Assistant | 搜索增强浮窗 | 场景匹配、来源筛选、AI 分析、扩展稳定性 |

### 4.2 第二层：能力型模块

这些模块功能价值高，但使用频率和路径复杂度不同。它们适合在主路径稳定后逐步打磨。

| 模块 | 打磨重点 |
|---|---|
| Skill Market | 分类、搜索、启用反馈、技能详情可读性 |
| Workflow | 模板创建、运行状态、暂停恢复、错误解释 |
| SOP | 流程块编辑、拖拽反馈、建议队列 |
| Memory | 层级视图、记忆提取、检索反馈、可信度表达 |
| Learning | 学习计划阅读、清单进度、复盘入口 |
| Creator Hub | 创作流水线、选题/脚本/复盘状态 |

### 4.3 第三层：系统稳定性模块

这些模块不一定直接被用户看见，但会决定整个产品是否可靠。

| 模块 | 打磨重点 |
|---|---|
| Backend 启停 | PID、端口、野进程、启动日志、错误诊断 |
| API 配置 | apiBase、环境变量、密钥管理、跨环境部署 |
| 数据库 | 迁移安全、重复数据、并发初始化、备份恢复 |
| 浏览器扩展通信 | CORS、Service Worker 保活、上下文失效 |
| Electron | 后端管理、路径适配、本地资源加载 |
| 构建部署 | Windows 路径、360 拦截、构建互斥、产物验证 |

### 4.4 第四层：设计系统与体验组件

这些是跨模块复用能力，应在修模块时逐步沉淀。

| 组件/规范 | 目标 |
|---|---|
| Toast | 统一成功、失败、警告、信息反馈 |
| Modal | 统一标题、关闭、保存、取消、危险操作确认 |
| Drawer | 统一预览、队列、详情面板 |
| Empty State | 统一空数据引导，不让页面显得坏掉 |
| Loading | 统一加载、骨架屏、进度条、长任务状态 |
| Error State | 统一错误解释、重试、复制诊断信息 |
| Button | 统一主按钮、次按钮、图标按钮、危险按钮 |
| Tag/Badge | 统一分类、状态、来源、优先级表达 |
| Toolbar | 统一搜索、排序、筛选、新建、更多操作 |
| Design Tokens | 色彩、字号、间距、边框、阴影、圆角变量化 |

## 5. 问题分级标准

### 5.1 P0：系统不可用

定义：用户无法进入系统，或核心数据存在丢失风险。

示例：

- 后端启动失败。
- 前端构建失败。
- 页面完全打不开。
- 数据库迁移导致数据丢失。
- 核心 API 返回 500 且无可用绕过方式。

处理规则：

- 立即修复。
- 不等待体验小方案。
- 修复后必须记录到对应模块问题文件。
- 必须有验证命令或复现路径。

### 5.2 P1：核心路径阻断

定义：页面能打开，但用户无法完成主要任务。

示例：

- 编辑按钮点击后无弹窗。
- 保存失败且无提示。
- 解析任务完成后文档列表不刷新。
- 搜索入口缺失，导致大量内容不可定位。
- 删除、取消、返回等关键操作不可用。

处理规则：

- 当前模块小方案必须处理。
- 修复前要写清核心路径。
- 修复后必须回归同一路径。

### 5.3 P2：明显体验问题

定义：不阻断任务，但明显增加理解成本、操作成本或视觉负担。

示例：

- 元信息拥挤。
- 按钮位置不明显。
- 空状态缺少引导。
- 错误提示只显示技术文本。
- 移动端布局挤压。
- hover/active/focus 状态不明显。

处理规则：

- 可与 P1 同轮处理，也可进入下一轮。
- 如果同类问题跨多个模块出现，应抽象为通用组件或规范。

### 5.4 P3：增强与美化

定义：不会显著影响任务完成，但能提升愉悦度、效率或品牌感。

示例：

- 轻量动效。
- 快捷键。
- 视觉精修。
- 首次使用引导。
- 主题个性化。
- 分享卡片增强。

处理规则：

- 进入体验 backlog。
- 不抢 P0/P1/P2 资源。
- 只有当主路径稳定后才集中处理。

## 6. 标准推进流程

每个模块小方案都按以下流程执行。

### 6.1 模块盘点

读取：

- `study-hub/project-memory/状态.md`
- 对应模块的 `状态.md`
- 对应模块的 `问题.md`
- 相关前端/后端文件
- 最近一次 UX 报告

输出：

- 当前模块能力清单
- 已知问题清单
- 相关文件清单
- 依赖模块清单

### 6.2 核心路径定义

为模块定义 1-3 条核心路径。

每条路径包含：

- 用户目标
- 入口
- 操作步骤
- 系统反馈
- 成功结果
- 失败恢复方式

示例：

```text
Wiki 编辑路径：
进入 Wiki -> 搜索/选择文章 -> 点击编辑 -> 修改内容 -> 保存 -> 返回阅读态 -> 确认内容更新
```

### 6.3 体验走查

按脚本执行核心路径和边缘场景。

检查维度沿用尼尔森十原则：

1. 系统状态可见性
2. 系统与现实世界匹配
3. 用户控制与自由
4. 一致性与标准
5. 防错
6. 识别而非回忆
7. 灵活性与效率
8. 美观与简洁
9. 容错
10. 帮助文档

### 6.4 问题分级

将走查结果写入：

- `study-hub/project-memory/ux/问题追踪.md`
- 对应模块的 `问题.md`

问题必须按 P0/P1/P2/P3 归类。

### 6.5 小方案制定

每个小方案只处理一个明确范围。

小方案必须写清：

- 本轮目标
- 本轮不做什么
- 交互调整
- 错误处理
- 边界测试
- 视觉调整
- 验收标准

### 6.6 实现修复

实现时遵循：

- 先加必要测试或验证脚本，再改代码。
- 优先复用已有组件和样式。
- 只抽象真实重复出现的东西。
- 不做无关重构。
- 不覆盖用户或其他 Agent 的未关联改动。

### 6.7 回归验证

每轮完成后至少验证：

- 目标路径是否完整走通。
- P0/P1 是否解决。
- 是否引入新错误。
- 构建或后端测试是否通过。
- UI 是否在主要视口下可用。

### 6.8 规范沉淀

如果修复中出现可复用规则，记录到：

- `study-hub/project-memory/ui/状态.md`
- `study-hub/project-memory/frontend/问题.md`
- `study-hub/project-memory/backend/问题.md`
- 或新建 UI/交互规范文档

## 8. 边界测试矩阵

每个模块不一定全部测试，但小方案要明确哪些适用。

| 场景 | 要验证的问题 | 常见风险 |
|---|---|---|
| 空数据 | 页面是否有引导 | 页面像坏掉、按钮不可见 |
| 单条数据 | 信息是否过少导致布局异常 | 卡片塌陷、空白过大 |
| 大量数据 | 列表、搜索、分页是否可用 | 卡顿、滚动困难、查找成本高 |
| 超长标题 | 文本是否溢出 | 按钮被挤出、布局错位 |
| 超长正文 | 阅读和编辑是否稳定 | 渲染慢、保存失败 |
| 特殊字符 | 中文、emoji、符号、路径字符 | 编码错误、文件名非法 |
| 网络错误 | 是否能解释失败 | 静默失败、技术报错外露 |
| API 超时 | 是否有长任务反馈 | 用户重复提交 |
| 重复点击 | 是否防重复提交 | 重复入库、重复任务 |
| 并发操作 | 多窗口/多任务是否稳定 | 状态覆盖、数据竞争 |
| 移动端 | 主路径是否可用 | 工具栏拥挤、弹窗溢出 |
| 深色模式 | 对比度是否足够 | 文本不可读 |
| 旧数据 | 迁移后是否兼容 | 字段缺失导致崩溃 |

## 9. 设计系统沉淀路线

### 9.1 第一阶段：统一反馈

优先沉淀：

- Toast
- Loading
- Error State
- Empty State

原因：这些直接影响用户对系统是否可靠的判断。

### 9.2 第二阶段：统一操作容器

沉淀：

- Modal
- Drawer
- Toolbar
- Confirm Dialog

原因：当前项目存在弹窗重复实现、工具栏样式不统一等问题。

### 9.3 第三阶段：统一视觉变量

沉淀：

- 主色
- 强调色
- 背景层级
- 边框
- 阴影
- 字号
- 间距
- 圆角

原因：当前存在硬编码色值和局部样式分散问题。变量化后，后续视觉美化成本会明显下降。

### 9.4 第四阶段：统一模块布局

沉淀：

- 页面标题区
- 左侧导航/索引
- 主内容区
- 右侧详情/预览
- 底部/浮动操作
- 全屏沉浸页面规则

原因：Study Hub 是多模块工具，布局一致性能降低学习成本。

## 10. 阶段节奏

### 10.1 第 0 轮：体验基线建立

目标：不急着修，先知道现状。

产物：

- 模块清单
- 核心路径清单
- UX 问题总表
- 每个高频模块的初始体验评分
- P0/P1/P2/P3 优先级队列

建议处理模块：

1. Wiki
2. Home
3. Automation
4. Journal
5. Search Assistant

### 10.2 第 1 轮：核心路径稳定化

目标：解决 P0/P1。

重点：

- 页面能打开。
- 核心按钮能触发。
- 保存/删除/编辑/搜索/解析能完成。
- 数据能刷新。
- 失败有提示。
- 后端启动和 API 配置更稳定。

### 10.3 第 2 轮：体验一致性

目标：解决关键 P2，并沉淀通用组件。

重点：

- Toast 统一。
- Modal 统一。
- Loading/Error/Empty State 统一。
- 工具栏和按钮统一。
- 页面信息层级调整。
- 色值开始变量化。

### 10.4 第 3 轮：产品美化与边界强化

目标：从“能顺利使用”提升到“愿意长期使用”。

重点：

- 移动端适配。
- 空数据体验。
- 长文本体验。
- 轻量动效。
- 首次使用引导。
- 视觉精修。
- 分享卡片、封面图、主题等情绪化体验。

## 11. 推荐模块顺序

### 11.1 第一优先级：Wiki

原因：

- 已有首次 UX 报告。
- 已发现明确 P1/P2。
- 知识库是 Study Hub 的核心沉淀场景。
- 适合作为本阶段样板模块。

建议小方案方向：

- Wiki 核心路径稳定化小方案。
- Wiki 搜索与新建入口小方案。
- Wiki 阅读与编辑体验小方案。

### 11.2 第二优先级：Home

原因：

- 高频入口。
- 决定第一印象。
- 已有最近文档、启动器、搜索等多个主路径。

建议小方案方向：

- Home 高频入口与状态反馈小方案。
- Home 卡片操作一致性小方案。

### 11.3 第三优先级：Automation

原因：

- 价值高，但边界多。
- 解析链路长，最需要状态可见性和错误恢复。

建议小方案方向：

- Automation 队列与进度反馈小方案。
- Automation 解析失败与重试体验小方案。

### 11.4 第四优先级：Journal

原因：

- 功能已完成 v1.0。
- 适合做产品气质和情绪化体验。

建议小方案方向：

- Journal 记录路径顺手度小方案。
- Journal 回顾与视觉温度小方案。

### 11.5 第五优先级：Search Assistant

原因：

- 浏览器扩展环境复杂。
- 需要真实浏览器场景验证。

建议小方案方向：

- 搜索助手场景匹配与来源筛选小方案。
- 搜索助手扩展加载与错误恢复小方案。

## 13. 验收标准

本阶段不是一次性完成，而是持续推进。阶段性验收可以分为三档。

### 13.1 最小完成

- 高频主路径模块都有核心路径定义。
- Wiki 至少完成一轮“走查 -> 小方案 -> 修复 -> 回归”。
- P0/P1 问题有清晰队列。
- 问题追踪表开始真实维护。

### 13.2 合格完成

- Wiki、Home、Automation 都完成至少一轮闭环。
- P0 问题清零。
- 高频路径 P1 问题基本清零。
- Toast、Loading、Error、Empty State 至少有初步统一方案。
- 每轮修改都有验证记录。

### 13.3 理想完成

- 高频模块综合体验评分达到 4.0/5 左右。
- P1 问题只作为新增回归偶发出现，不长期积压。
- P2 问题有稳定处理节奏。
- 设计系统形成初版文档。
- 后续新增功能都默认带核心路径、边界测试和体验验收。
