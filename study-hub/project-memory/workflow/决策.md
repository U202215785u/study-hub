# Workflow 模块设计

> 状态：R0 规划完成，待 R2 实现
> 创建：2026-06-06
> 参考：Codex CLI workflow 生态（codex-workflows, Symphony, TheWorkshop）

## 目标

在 Study-Hub 中构建 **Workflow 编排框架**：
- Workflow 用 **YAML 模板文件**定义，存于项目目录，可复用
- 通过对话即可调用执行（管家层对接）
- 编排层只做步骤调度 + 状态管理，实际能力调用已有工具（WebBridge、MCP、API）
- 第一个用例："设计临摹"（Pinterest → Eagle → 反推提示词 → image2 生成）
- 框架本身通用，设计临摹只是首个 workflow

## 核心设计决策

### DEC-WF-001：步骤原子类型 —— 3 种调度模式 + gates

> 借鉴 Codex TheWorkshop 的 Gates 机制：Agreement Gate / Dependency Gate / TruthGate / Reward Gate

步骤按**调度模式**分为 3 种，gates 是挂在步骤前后的可选项：

| 类型 | 调度模式 | 说明 |
|------|----------|------|
| `tool` | 调工具，等结果，继续 | 浏览器操作、API 调用、AI 分析——引擎不关心调谁 |
| `ask` | 暂停，在对话中等回复 | "这些提示词可以吗？"——人在聊天界面内决策 |
| `human` | 暂停，等外部操作完 | "把图存到 Eagle，好了点继续"——人离开对话去操作 |

每步可选挂载：

| Gate | 位置 | 说明 |
|------|------|------|
| `before` | 步骤前 | 确认输入/参数（Agreement Gate） |
| `after` | 步骤后 | 确认结果/满意（TruthGate + Reward Gate） |

**废弃了 `control` 类型** —— 条件分支/循环放 YAML 控制流字段（`if`/`loop`），不混入步骤。

### DEC-WF-002：工具注册与 recipe 分离

> 借鉴 Codex：subagent TOML 定义（能力） + codex-workflows recipe（流程），两者解耦

```
YAML recipe（做什么、什么顺序、数据怎么流）
    ×
工具注册表（谁能干这个活 —— WebBridge / MCP / API / 本地脚本）
```

YAML 里 `tool: browser` 只是引用一个已注册的工具名，引擎去注册表里找对应的执行器。

### DEC-WF-003：状态机驱动

> 借鉴 Symphony：用看板状态驱动编排器行为

每个步骤 5 个状态，引擎只看状态决定下一步：

```
pending → running → done
                 → error → retry/skip/stop
                 → paused（等人操作）
```

与现有 automation 的 `STEPS` 机制完全兼容，只新增 `paused` 状态。

### DEC-WF-004：步骤间显式数据流

> 借鉴 Codex 子代理上下文隔离：不依赖 AI 记忆，明确传数据

```yaml
steps:
  - id: search
    tool: browser
    action: "在 Pinterest 搜索 {{.params.keyword}}"
    output: screenshots    # ← 给后续步骤引用的变量名

  - id: select
    ask: "哪些图？"
    input: "{{.search.screenshots}}"   # ← 显式引用上一步输出
```

引擎维护一个 `context` dict，每个步骤的 output 写入，input 从 context 读取。

### DEC-WF-005：复用现有基础设施

不另起炉灶，直接跑在现有 automation 架构上：

| 基础设施 | 来源 | 改动 |
|----------|------|------|
| ThreadPoolExecutor 任务队列 | `automation.py` 现有 | 不变 |
| `_tasks` dict + 状态查询 API | 现有 | 加 `paused` 状态 |
| 细粒度步骤追踪 `STEPS` | 现有 | 从 YAML 动态生成 |
| 前端进度轮询 | 3 秒轮询 `/queue/status` | 增加暂停/继续按钮 |
| API 路由 | `/automation/` | 新增 `/workflow/` 路由组 |

### DEC-WF-006：YAML 模板存放位置

`study-hub/workflows/` 目录，项目级。后续需要跨项目复用时再升到用户级记忆。

## YAML 模板 Schema（v1 草案）

```yaml
# study-hub/workflows/design-copy.yml
name: 设计临摹
desc: Pinterest 找参考 → 反推提示词 → AI 生成
version: "1.0"

params:                          # 调用时传入的参数
  - name: keyword
    type: string
    ask: "要临摹什么风格？"       # 调用时没传就反问

steps:
  - id: search
    tool: browser
    action: "打开 Pinterest，搜索 {{.params.keyword}}，截屏前 20 张"
    output: screenshots

  - id: select
    ask: "哪些值得临摹？给序号（如 1,3,5）"
    input: "{{.search.screenshots}}"
    output: selected_indices

  - id: eagle_save
    human: "在 Eagle 中保存选中的图片 {{.select.selected_indices}}，完成后点继续"

  - id: reverse_prompt
    tool: ai
    action: "分析选中图片，反推中英双语 Stable Diffusion 提示词"
    input: "{{.select.selected_indices}}"
    output: prompts
    after:
      ask: "提示词：{{.prompts}}。要改吗？直接回复最终版"

  - id: generate
    tool: api
    endpoint: image2
    params:
      prompt: "{{.reverse_prompt.prompts}}"
    output: results
    after:
      ask: "生成结果：{{.results.images}}。满意吗？"
```

## 引擎执行循环（伪代码）

```python
def execute_workflow(yaml_path: str, params: dict) -> dict:
    template = load_yaml(yaml_path)
    context = {"params": params}
    
    for step in template["steps"]:
        context["_current_step"] = step["id"]
        
        # before gate
        if "before" in step:
            result = execute_gate(step["before"], context)
            merge_to_context(context, result)
        
        # 主步骤
        step_type = get_step_type(step)  # tool | ask | human
        if step_type == "tool":
            result = execute_tool(step, context)
        elif step_type == "ask":
            result = pause_and_ask(step, context)  # → paused
        elif step_type == "human":
            result = pause_for_human(step, context) # → paused
        
        merge_to_context(context, step.get("output"), result)
        
        # after gate
        if "after" in step:
            result = execute_gate(step["after"], context)
            merge_to_context(context, result)
    
    return context
```

## 与现有 automation 的关系

```
automation（现有）          workflow（新增）
─────────────────          ────────────────
硬编码 pipeline             YAML 驱动 pipeline
只有 Python 函数调用         tool/ask/human 三种调度
无暂停点                    支持 paused 状态
抖音/B站/小红书专用          任意流程通用
```

workflow 不会替代 automation，而是让 automation 成为 workflow 的一个**工具提供方** —— 抖音解析可以变成 workflow 的一个 `tool` 节点。

## 工具注册表（初版）

```python
TOOL_REGISTRY = {
    "browser": KimiWebBridgeExecutor,   # 通过 WebBridge skill
    "ai": ClaudeExecutor,               # 通过 Claude CLI
    "api": HTTPExecutor,                # 通用 HTTP 请求
    "douyin-parse": DouyinExecutor,     # 现有自动化能力
    "bilibili-parse": BilibiliExecutor,
    "xhs-parse": XHSExecutor,
}
```

新增工具只需注册一个新 key，不改引擎。

### DEC-WF-007：workflow 使用独立 `_tasks` 字典

> 与设计文档 DEC-WF-005「复用现有 _tasks 字典」不同，实际实现选择了独立字典。

设计文档建议直接扩展 `automation.py` 的 `_tasks`，但实现时发现两类任务结构差异大：
- automation task: `module_id` / `input` / 硬编码 STEPS
- workflow task: `template_path` / `params` / 动态 YAML steps

混合存储会导致字段混乱、状态判断复杂。因此 workflow 使用独立的 `_workflow_tasks` 字典（在 `engine.py` 中），但复用相同的模式（`ThreadPoolExecutor`、`threading.Lock`、`uuid[:8]` 短 ID、`datetime.now().isoformat()` 时间戳）。

### DEC-WF-008：手写模板变量解析，不引入 Jinja2

模板变量语法 `{{.step_id.key}}` 足够简单，两层路径解析覆盖所有当前需求。手写实现不到 30 行，避免引入额外依赖和模板注入风险。

### DEC-WF-009：步骤类型推断兼容隐式写法

YAML 步骤支持两种写法：
1. 显式：`type: tool`（推荐，语义清晰）
2. 隐式：有 `tool` 字段即推断为 tool，有 `ask` 字段即推断为 ask（兼容设计文档）

优先使用显式 `type` 字段。隐式推断为向后兼容。

### DEC-WF-010：大白话创建 + 模板管理 —— 降低使用门槛

> 用户不需要懂 YAML，不需要知道工具怎么注册。

**白话文创建流程：**
1. 用户在输入框用自然语言描述想做的事（如"打开百度搜猫，截图，AI分析"）
2. 前端 POST `/workflow/create-from-text` → 后端调 DeepSeek API，用 YAML Schema Prompt 转译为合法 YAML
3. 保存到 `workflows/` 目录，返回给前端展示

**模板管理：**
- `GET /templates/{filename}` — 获取 YAML 原始内容（编辑用）
- `PUT /templates/{filename}` — 保存编辑后的 YAML
- `DELETE /templates/{filename}` — 删除模板
- `POST /templates/{filename}/copy` — 复制模板
- 前端提供：✏️ 编辑（YAML 编辑器弹窗）、📋 复制、🗑 删除

**工具自动注册：**
- `workflow/__init__.py` import `executors` 模块 → 模块加载时自动 `register()` 三个执行器
- 用户完全感知不到——页面上 `/workflow/tools` 可以看到已注册工具列表
- 加新工具只需在 `executors.py` 里写一个函数 + 一行 `register()`

### DEC-WF-011：工具显式输入输出 Schema

每个工具有明确的 input/output 契约（`ToolDef` 类），引擎据此校验和对接：

**input 定义：** 每个字段有 type（select/text/url/textarea/json/ref）、label（人类可读）、required、placeholder、options
**output 定义：** 分为 text 型（直接展示）和 file 型（存 workspace，前端提供下载链接）

步骤 YAML 格式从模糊的 `action: "做什么"` 改为：
```yaml
input:
  action: navigate
  url: "https://..."
output:
  label: "搜索结果截图"
```

引擎为每次运行创建独立 workspace 目录（`workflow-runs/{task_id}/`），文件产出存于此，通过 `/workflow/output/{task_id}/{filename}` 下载。

### DEC-WF-012：AI 调用从 httpx 改为 requests + SSL 降级

workflow engine 跑在 ThreadPoolExecutor 线程中，httpx 的异步 SSL 上下文在子线程里不可靠（SSL UNEXPECTED_EOF）。改用 `requests` 库同步调用 + 失败自动 `verify=False` 降级 + 3 次重试。白话文生成的 AI 调用同理。

### DEC-WF-013：执行记录展开/折叠 + 归档

- 任务卡片默认收起（只显示模板名 + 状态），点击展开看详情
- 运行中/暂停的任务自动展开
- 完成/失败的任务可归档（📦），从主列表隐藏
- 右上角显示归档数量，可切换查看
