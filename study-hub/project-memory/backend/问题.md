- ISS-001: API key 硬编码在 ai_client.py — high — 2026-05-29 — open

  - 影响：生产环境泄露内部信息
  - 建议：生产环境只返回通用错误消息，详细日志写入文件
- ISS-010: CORS 配置过宽（chrome-extension://*）— medium — 2026-05-29 — open
  - 影响：生产环境安全隐患
  - 建议：生产环境收紧为具体域名
- ISS-022: `_sanitize_pid_file()` 使用 `localhost` 而非 `127.0.0.1`，Windows IPv6 解析可能误判 — medium — 2026-05-30 — open
  - 影响：`main.py` 第 83 行 `sock.connect_ex(("localhost", 8741))`，在 Windows 上 `localhost` 可能解析为 `::1`（IPv6），而 uvicorn 绑定的是 `0.0.0.0:8741`（IPv4），导致误判端口未监听、清理有效 PID 文件
  - 根因：Python socket 在 Windows 上优先尝试 IPv6，`localhost` → `::1`，但服务只监听 IPv4
  - 建议：将 `"localhost"` 改为 `"127.0.0.1"`
  - 文件：`backend/main.py`

- ISS-024: Kimi Background Bash 15s 超时杀死后端进程 — high — backend/deploy — 2026-05-30 — open
  - 影响：用 Kimi `run_in_background=true` 启动后端，15s 后任务超时，后端进程被系统杀掉，前端所有 API 返回 500
  - 根因：Kimi Background Bash 有默认超时（15s），后端启动后持续运行，超时后任务被强制终止
  - 解决：改用 Shell 后台进程（`py backend/main.py > log 2>&1 &`），脱离 Kimi 任务管理
  - 长期方案：始终用 `后台启动.bat` 或 `start-background.ps1` 启动后端
  - 注意：手动 `&` 启动不会写 `data/server.pid`，stop 脚本可能找不到进程，需手动补写 PID 文件或改用启动脚本
  - 相关：ISS-018（PID 文件僵尸化）、ISS-012（后台启动脚本）、ISS-027（野进程）

- ISS-027: "野"进程问题——手动启动的服务无 PID 文件，脚本无法管理 — high — backend/deploy — 2026-05-30 — open
  - 影响：用户/Agent 直接用 `python backend/main.py` 启动的服务没有 PID 文件，`stop-background.ps1` 找不到它，端口一直被占用
  - 根因：绕过 `后台启动.bat` 直接启动，未写入 `data/server.pid`
  - 解决：手动终止进程，以后统一用脚本启停
  - 长期方案：DEC-027（禁止手动启动，统一使用启动脚本）
  - 相关：ISS-018（PID 僵尸化）、ISS-024（Kimi Bash 超时）、ISS-025/026（Python 环境混乱导致被迫手动启动）
  - 教训：后端-owner 和 deploy-owner 必须明确——任何情况下都不要手动 `python main.py`，一律用 `后台启动.bat`

- ISS-018: 多代理并发时后端 PID 文件僵尸化导致端口冲突 — high — 2026-05-30 — **resolved**
  - 根因：`data/server.pid` 记录的是已死进程的 PID，新代理读到后误以为服务在跑，实际端口未监听。详细根因包括：
    1. `start-background.ps1` 先检查端口占用，再检查 PID 文件，但两者逻辑不互通 —— 端口空闲时不会清理僵尸 PID 文件
    2. `main.py` 的 `_sanitize_pid_file()` 端口检测使用 `connect_ex("localhost", 8741)`（原为 `"127.0.0.1"`），在部分网络配置下可能连接失败（误判为端口未监听）—— 见 ISS-022
    3. PID 文件最初写入的是 `cmd.exe` 的 PID（父进程），而非实际 `python.exe` 的 PID，导致 stop 脚本可能杀错进程
    4. 无全局锁机制，Agent 快速连续调用启动脚本时可能并发创建多个实例
  - 修复：
    1. `start-background.ps1` 启动时校验端口占用 + 进程存在性；端口占用时直接退出，端口空闲时清理僵尸 PID
    2. `main.py` lifespan 增加 `_sanitize_pid_file()` 启动清理：验证 PID 存在性 → 验证端口监听 → 任一失败则删除 PID 文件
    3. `start-background.ps1` 通过 `Get-NetTCPConnection` 端口反查获取实际 python 进程 PID 写入文件
    4. `stop-background.ps1` 支持按端口强制终止（三级回退：端口 → PID 文件 → 命令行匹配）
  - 已知限制：ISS-022（localhost IPv6 误判）仍为 open，需单独修复
  - 文件：`backend/start-background.ps1`、`backend/stop-background.ps1`、`后台启动.bat`、`后台停止.bat`、`backend/main.py`
- ISS-019: 多代理同时构建导致 frontend/dist 产物随机覆盖 — high — 2026-05-30 — **resolved**
  - 根因：`build.sh` 使用固定临时目录 `/c/temp/study-hub-fe-build`，两个代理同时执行时互相覆盖源码和产物
  - 修复：`build.sh` 增加文件锁机制（`.lock` 标记文件 + 5分钟超时），第二个构建会等待第一个完成
  - 文件：`frontend/build.sh`
- ISS-020: 数据库 init_db() 在多实例启动时可能触发表重建 — medium — 2026-05-30 — **resolved**
  - 根因：`init_db()` 每次启动都执行完整 `CREATE TABLE IF NOT EXISTS`，多个 uvicorn 同时写同一 SQLite 文件可能竞争损坏
  - 修复：增加 `db_exists` 判断，已有数据文件时跳过初始化 DDL
  - 文件：`backend/database.py`

## 已解决问题
- ISS-012: 后端服务无法通过后台任务持续运行 — critical — 2026-05-29 — **resolved**
  - 根因：Kimi CLI 后台任务 60s 超时；PowerShell `Start-Process` 子进程会被父会话 Job Object 连带销毁
  - 修复：新增 `start-background.ps1` / `stop-background.ps1` / `后台启动.bat` / `后台停止.bat`，使用 `cmd /c start /min` 创建真正脱离父会话的独立进程
  - 文件：`start-background.ps1`、`stop-background.ps1`、`后台启动.bat`、`后台停止.bat`
- ISS-015: automation 模块摘要文档重复入库 — high — 2026-05-29 — **resolved**
  - 根因：automation 业务层无去重逻辑，documents 表缺少唯一约束
  - database 层修复：新增 `idx_doc_source_hash(source, content_hash) WHERE content_hash != ''` partial unique index，作为数据库层最后防线
  - 注意：需重启服务使 `init_db()` 创建索引；已有重复数据需通过 `/documents/cleanup` 清理
  - 文件：`backend/database.py`
