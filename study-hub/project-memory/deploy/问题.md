## 开放问题

- ISS-025: Windows `python` 命令是 Microsoft Store 重定向器，exit code 49 无法执行 — critical — 2026-05-30 — open
  - 影响：在 Git Bash / Kimi CLI 中执行 `python` 命令，实际调用的是 `C:\Users\...\WindowsApps\python.exe`（Microsoft Store 重定向器），返回 exit code 49，完全不执行任何代码
  - 根因：Windows 10/11 默认将 `python` 命令关联到 Microsoft Store 的 AppInstallerPythonRedirector.exe，未安装 Store 版 Python 时直接失败
  - 影响范围：所有依赖 `python` 命令的脚本、Kimi CLI 的 Shell 工具、手动命令行操作
  - 解决：使用完整路径 `C:\Users\Administrator\AppData\Local\Programs\Python\Python312\python.exe`
  - 长期方案：`start-background.ps1` 已硬编码 Python 路径，但应考虑从 `.env` 或注册表读取
  - 相关：ISS-026（venv 被污染）、ISS-027（野进程）
  - 教训：Windows 环境下永远不要假设 `python` 命令可用，启动脚本必须显式指定 Python 路径

- ISS-026: venv 被污染：`python.exe` 被替换为 `HD_python.exe` — high — 2026-05-30 — open
  - 影响：`venv\Scripts\python.exe` 变成了 `HD_python.exe`，无法正常启动后端，依赖 venv 的脚本全部失效
  - 根因：未知（可能是 HD 相关工具/插件/安全软件修改了 venv 的可执行文件）
  - 影响范围：所有依赖 venv 的启动方式、后台启动脚本（如果改为用 venv python）
  - 解决：暂时使用系统 Python（`Python312\python.exe`），不使用 venv
  - 长期方案：重建 venv，或改用 `uv` / `poetry` 管理环境，或调查 `HD_python.exe` 的来源
  - 相关：ISS-025（python 命令失效）
  - 教训：venv 不是绝对可靠的，生产部署脚本应支持 fallback 到系统 Python

- ISS-027: 旧服务是"野"进程（无 PID 文件），脚本无法识别和停止 — high — 2026-05-30 — open
  - 影响：之前手动 `python backend/main.py` 启动的服务（PID 8812）没有写入 `data/server.pid`，`stop-background.ps1` 找不到它，导致端口 8741 一直被占用，新服务无法启动
  - 根因：用户/Agent 直接用 `python backend/main.py` 启动，而不是用 `后台启动.bat` → `start-background.ps1`
  - 影响范围：端口冲突、服务无法重启、代码修改后不生效
  - 解决：手动用 `taskkill /F /PID 8812` 或 PowerShell `Stop-Process` 终止
  - 长期方案：
    1. **禁止手动启动**：所有启动必须通过 `后台启动.bat`
    2. `stop-background.ps1` 增加"按端口强制终止"作为最终回退（已部分实现）
    3. `start-background.ps1` 启动时如果端口被占用且找不到 PID 文件，直接报错并提示手动终止
  - 相关：ISS-018（PID 僵尸化）、ISS-024（Kimi Bash 超时杀进程）
  - 教训：进程管理必须有统一入口，野进程是运维噩梦

## 已解决问题
- ISS-028: `start-background.ps1` 端口检查把 TIME_WAIT 误判为端口占用 — high — 2026-05-30 — **resolved**
  - 影响：停止服务后，端口 8741 上有 TIME_WAIT 状态的残留连接（OwningProcess=0），脚本误判为"端口被占用"，导致无法重启
  - 根因：`Get-NetTCPConnection -LocalPort 8741` 返回所有状态的连接，包括 TIME_WAIT/CLOSE_WAIT/FIN_WAIT 等已关闭的残留状态
  - 修复：端口检查时增加 `Where-Object { $_.State -eq 'Listen' }`，只检查真正在监听的连接
  - 文件：`backend/start-background.ps1`
  - 教训：端口占用检查必须区分 TCP 连接状态，TIME_WAIT 是正常残留，不应阻止新服务启动

- ISS-029: `stop-background.ps1` 变量名 `$Pid` 与 PowerShell 自动变量冲突 — high — 2026-05-30 — **resolved**
  - 影响：停止脚本执行到 `$Pid = $PortProc.OwningProcess` 时报错"无法设置变量 PID，因为该变量为只读"
  - 根因：`$Pid` 是 PowerShell 的**自动变量**（只读），存储当前进程的 PID，不能赋值
  - 修复：将 `$Pid` 改为 `$ProcId`
  - 文件：`backend/stop-background.ps1`
  - 教训：PowerShell 有多个自动变量（$Pid, $_, $PSItem, $Error 等），命名变量时必须避开

- ISS-030: PID 文件可能写入无效内容（如 `%!`）— high — 2026-05-30 — **resolved**
  - 影响：`start-background.ps1` 中 `echo %! > server.pid` 在 cmd 中 `%!` 不是有效变量，写入的是字面量 `%!`，导致后续读取 PID 时解析失败
  - 根因：`InnerCmd` 使用 `echo %!` 试图写入 cmd 的进程 ID，但 `%!` 在 Windows cmd 中不是预定义变量（Linux bash 的 `$!` 才是后台进程 PID）
  - 修复：
    1. 删除 `echo %! > server.pid`（无效命令）
    2. 启动后通过 `Get-NetTCPConnection` 端口反查获取实际 PID 写入文件
    3. 增加 PID 文件内容校验：读取时正则匹配 `^\s*(\d+)\s*$`，不匹配则视为无效并清理
  - 文件：`backend/start-background.ps1`、`backend/stop-background.ps1`
  - 教训：跨平台脚本要注意 shell 变量差异，`$!` 是 bash 特性，cmd 中没有等价物
